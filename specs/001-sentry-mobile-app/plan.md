# Implementation Plan: Farm Sentry Mobile App

**Branch**: `001-sentry-mobile-app` | **Date**: 2026-02-26 | **Spec**: [`spec.md`](spec.md)  
**Input**: Feature specification from `specs/001-sentry-mobile-app/spec.md`

## Summary

Build a Flutter mobile application (iOS 16+ / Android 10+) serving as the tactical interface for the Farm Sentry autonomous security system. The app connects to the sentry's MQTT broker over TLS, ingests real-time `TelemetryRecord` messages, renders animated threat markers on an offline-capable map HUD, triggers high-priority local alarms, and provides on-demand MJPEG video verification and manual turret override. Architecture is map-centric, MQTT-primary, and optimised for low-bandwidth rural operation.

**Approach**: Feature-sliced Flutter project using Riverpod for state management, `mqtt_client` for TLS MQTT, `flutter_map` + tile caching for offline maps, `drift` for persisted alert log, and `flutter_secure_storage` for credentials.

## Technical Context

**Language/Version**: Dart 3.x / Flutter 3.x (latest stable)  
**Primary Dependencies**: `flutter_riverpod`, `mqtt_client`, `flutter_map`, `flutter_map_tile_caching`, `drift` (SQLite), `flutter_secure_storage`, `flutter_local_notifications`, `flutter_background_service`, `geolocator`, `http`  
**Storage**: SQLite via `drift` (alert log); `flutter_secure_storage` (credentials)  
**Testing**: `flutter_test`, `mocktail`, `drift` test utilities  
**Target Platform**: iOS 16+, Android 10+ (API 29+)  
**Project Type**: Mobile app  
**Performance Goals**: Map marker updates ≤ 2 s after MQTT publish (FR-006); HIGH-tier notification delivery ≤ 3 s (SC-001); smooth rendering of ≥ 10 simultaneous animated markers (SC-005)  
**Constraints**: Offline tile caching required; all MQTT over TLS port 8883; no unencrypted fallback; video stream local-network-only; background MQTT must survive phone lock  
**Scale/Scope**: Single-sentry deployment; alert log up to thousands of entries; 8 screens; ~25 FRs

## Complexity Tracking

| Deviation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|--------------------------------------|
| Flutter mobile app layer (new language: Dart) | The mobile interface is the primary operator surface; no cross-platform framework was in the constitution's stack | A native Swift/Kotlin app would require maintaining two separate codebases; a web-only interface cannot provide background alarms or lock-screen notifications |
| `drift` ORM over raw `sqflite` | Alert log requires complex time-range queries, automatic purge via triggers, reactive streams, and safe schema migration | Raw `sqflite` lacks type safety and compile-time query validation — risky for a security-critical log that must survive across app updates |
| `flutter_background_service` foreground service | MQTT must stay connected while the phone is locked to deliver HIGH-tier alarms | Standard background isolates are aggressively killed on both iOS and Android; a foreground service with notification is the only reliable cross-platform solution |
